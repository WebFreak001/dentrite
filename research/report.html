1. TL;DR and decision table

Recommendation. Build dentriteui as a retained library. A tree of nodes persists between frames. Signals carry app state into node properties, layout uses Flutter-style box constraints with cached measurements, and only what changed is laid out and painted again. Views that are easier to write in immediate mode, such as a 3D viewport or the hex and disassembly views, become immediate islands. The tree hands each island a rect, and the island runs an immediate pass inside it. This is path C, built on path B. The islands run on dentriteui's own immediate core (immediate.d, path A2), which shares the layout engine, renderer and widget looks with the tree. ddui stays dd's immediate-mode library as it is. In everything that makes egui look good, grow toward egui anyway: a real text stack, feathered anti-aliased meshes, theme tokens, repaint scheduling and AccessKit through its C API. Keep messages and commands at the application boundary, and the mailbox for the backend. The core of each part is worked out and tested in examples/, with switch criteria in section 11.

Why.

  1. It is dd's direction. dentriteui is new, written in D, and has no UI library underneath. SDL, the font libraries and AccessKit's C API are the only outside code. ddui already covers immediate-mode needs, and inside a full UI immediate mode is wanted only for the views that need it.
  2. A retained tree is cheapest per change and silent when idle. One hit count costs 1.3 µs at 50 rows, and a pointer move costs only a hit test (11.5). A debugger's steady state is many small changes: hit counts, registers, thread states.
  3. Accessibility, focus, animation and tests want a stable tree. A node maps one to one to an accessibility node, and keeps its focus and animation state for as long as it lives. Makepad builds one semantic tree for screen readers, UI tests and automation (3.8). AccessKit takes incremental updates (10).
  4. Layout is exact from the first frame and cheap after it. layout.d caches measurements and lays out again only the relayout boundaries that changed (6.4).
  5. Immediate mode stays where it pays. hybrid.d's island re-runs only when a signal it read changes, when it gets input or when its rect moves, and costs nothing while idle (9.1). Moving the islands from ddui to immediate.d gives both sides one renderer and one look.
  6. Polish does not depend on architecture. Rerun and PdfCraft are polished, large egui apps. The egui fork behind PdfCraft carries 23 patches, and almost all of them are text, IME, bidi, keyboard layout and clipboard fixes (3.2.4). That work is the same in any architecture.

The risks are B's: it needs the most infrastructure, and it brings node ownership and disposal bugs and a signal graph to debug. Its measured weak spot is structural change. Building the panel or switching the filter costs about as much as an A2 frame and allocates about 1.4 KiB per row. M2 targets that, and 11.4 says when to fall back.

2. Vocabulary

Retained mode
The library keeps a tree of widget objects between frames and the application mutates it. WinForms, Qt, GTK and the DOM work this way.
Immediate mode
The application describes the UI every frame by calling functions, and the library keeps only small ID-keyed state. The term describes the API, not the renderer. Dear ImGui's wiki: "IMGUI does not mean that the library doesn't retain data".
Declarative
You state what the UI is for a given state, not the steps that change it. React, Compose, SwiftUI and QML are declarative, and so is immediate-mode code.
Reactive
A change to state reaches its dependents automatically, with no manual "update the label" call.
Reconciliation
Matching a new description against the existing tree to decide which nodes to keep, update, create or delete. Keys tell it which list item is which.
Virtual DOM (VDOM)
A cheap description tree, rebuilt on every update and diffed against the previous one to patch the real tree.
Fine-grained reactivity
Updates go straight to individual node properties through a dependency graph. No component re-runs and nothing is diffed.
Signal, memo, effect
A signal is a writable reactive value. A memo (computed) is a cached derived value that recomputes when its inputs change. An effect is a side effect that re-runs when anything it read changes.
Owner scope
A node that owns the effects created inside it and disposes them together, for example Solid's createRoot or alien-signals' effectScope.
Positional memoization
State and cached results keyed by where a call sits in the code and in the call tree, such as Compose's remember or React hooks.
Layout pass
The traversal that computes sizes (measure) and positions (arrange or place).
Hit testing
Finding which element is under a point.
Invalidation
Marking something stale so it gets recomputed: layout, paint, or a derived value.
Damage region
The part of the screen that changed and must be repainted. Win32's InvalidateRect adds to it.
Virtualization
Building only the visible rows, so cost scales with the viewport and not with the data.
Repaint scheduling
Deciding when the next frame runs: on input, on request, or after a timeout. This is what sets idle CPU in every architecture.
ID
A widget's identity across frames. Immediate libraries derive it from labels, pointers, call sites or pushed keys. Retained libraries get it for free from object identity.

3. Architecture families

3.1 The running example

A debugger breakpoints panel is used throughout:

  • a filter text box (local UI state)
  • a list of breakpoints, each with file:line, an enabled checkbox and a hit count that updates while the program runs (list identity, frequent external updates)
  • an "N of M shown" label (derived state)
  • a "Remove disabled" button (an edit that changes list membership)

Each family below covers its mental model, where state lives, how a hit-count change reaches the screen, and what costs CPU. Then comes the panel in that framework's language and its D equivalent.

3.2 Immediate mode: Dear ImGui, egui, microui/ddui

3.2.1 Model, state, update path, cost

Model. The UI is a function called every frame. A widget call draws itself and returns its interaction result in the same call: if (mu_button(ctx, "Remove disabled")). The library keeps only small state keyed by ID: the hovered, pressed and focused widget, scroll offsets, window rects, open flags.

State. It lives in the application. Widgets take pointers or references into it (microui and ImGui take int* or bool*, egui takes &mut). There is no second copy, so nothing can get out of sync. The egui README puts it as "You don't have to worry about app state and GUI state being out-of-sync".

Update path. An event wakes the loop, the whole UI function runs, it emits commands or meshes, and the frame is rendered. A hit-count change shows on the next frame that runs.

CPU. Every frame that runs executes the UI code for everything not culled. egui: "For most cases you can expect egui to take up 1-2 ms per frame", and it "only repaints when there is interaction (e.g. mouse movement) or an animation, so if your app is idle, no CPU is wasted". The classic trap is a huge scroll area. The fix is to build only visible rows (ScrollArea::show_rows, Dear ImGui's ImGuiListClipper).

3.2.2 egui's tricks for "retained" behaviour

  • Per-ID memory. ctx.data_mut(|d| d.get_temp_mut_or_default::<T>(id)) gives any widget typed state keyed by Id, either temporary or persisted with serde (get_persisted_mut_or_default). Collapsing headers, scroll areas and text edits keep their state there. immediate.d's memoryFor does the same and drops entries not used in a frame.
  • IDs. Auto IDs come from the parent ID plus a counter. Loops use push_id or id_salt. show_rows calls skip_ahead_auto_ids(min_row) so a row keeps its ID while scrolling.
  • Sizing passes and one-frame delays. A Grid or Window does not know its size until its contents have run, so egui remembers last frame's size and guesses on the first frame ("first-frame jitter"). Context::request_discard(reason) throws away the visual output and runs another pass, capped by Options::max_passes (default 2). UiBuilder::sizing_pass() runs content invisibly just to measure it.
  • Repaint requests. request_repaint() works from any thread once the integration installs a callback, as eframe does. request_repaint_after(d) keeps the smallest pending delay, which gives timers at zero idle CPU.
  • Text layout cache. epaint's GalleyCache memoizes LayoutJob to Galley by hash and evicts entries not used during a frame. Re-running the UI every frame is cheap because text is not re-shaped.

3.2.3 What reading and running ddui showed

Read at c9bff89 (2026-11-02, cloned from github.com/dd86k/ddui because /workspace/Projects/ddui is not mounted in this container). examples/panel_ddui.d drives it headless.

  • One pass, placed while declared. mu_layout_row(ctx, n, widths, height) sets column widths (negative means relative to the right edge) and mu_layout_next hands out the next rect. A parent cannot measure its children. Conclusion 1 of the previous session holds.
  • A settle frame. mu_scrollbars compares last frame's content_size with last frame's body rect, and in frame 0 that body is zero. So frame 0 reserves a scrollbar and lays the panel out 12 px narrower. "Remove disabled" sits at x=260 in frame 0 and at x=272 in frame 1. A test click aimed at frame-0 coordinates missed. Both facts are now asserted in the tests. This is the same class of problem egui documents as first-frame jitter.
  • IDs follow memory addresses. mu_checkbox and mu_textbox hash the pointer value of the bound variable under the ID stack. When "Remove disabled" reallocates the array, every checkbox ID changes. That is harmless for hover but would drop keyboard focus.
  • Idle is already handled. The demo blocks on SDL events (16 ms timeout) and runs the UI only when events arrived. mu_frame_dirty then hashes the command list and skips rendering when nothing changed. It is cheap and robust, but every mouse move still runs a full UI pass.
  • Renderer contract. Five command types (JUMP, CLIP, RECT, TEXT, ICON) in a 32-byte union, integer rects, and text kept in an arena by index. The demo font is a baked 128x128 ASCII atlas.
  • Reusable: the command-list contract and frame hash, the style struct idea, text measure callbacks, FNV-1a IDs and the ID pool, and the widget state machines: textbox selection and word motion, menus and popups, tab focus. Also vddhx, dd's SDL3 hex editor on ddui, is the closest existing thing to the debugger's memory view.

3.2.5 nanoui: deferred layout in shipped apps

justrach/nanoui, read at 1b43b1a (2026-11-14), is a Zig framework for desktop and mobile apps. Its native UI is immediate mode with deferred layout, which is this report's path A2, and real apps run on it: a terminal, an activity monitor, a mail client, a screen recorder. It borrows gpui's surface: elements styled by method chains (ui.div(c).row().gap(8).bg(...)), a virtualized list after uniform_list, gpui's shadow shader, a component kit after GPUI Kit and animation after gpui-motion. The architecture is not gpui's. There are no entities and no notify. One view function of the app's state runs on every event, widget calls return their interaction, and layout is its own two-pass flexbox, not Taffy.

  • A frame. frame.zig builds the view, then builds it again while a pass changed state, at most four passes, with the input's presses and key edges spent after the first. Then it measures, arranges and paints into GPU instances, once. In its words, "the screen never lags the state": no drawn frame shows the state from before a click. immediate.d's Ui.frame now does the same.
  • Memory. Nodes live in one array, linked by u32 indices (parent, first child, next sibling), and begin resets a frame arena that keeps its capacity. A widget's state between frames is a fixed 48-byte slot in a hash map. No node is a heap object of its own. That is M3's frame arena, and it would also end the pinned old frames of 11.5, finding 9.
  • Scrolling without a build. retain.zig keeps the last frame's GPU instances. An event that only moved a scroll offset shifts them, and the rects under the scrolled box, instead of building, laying out and painting. Any press, key, gesture, animation, resize, virtual list or nested clip falls back to a full frame, and so does an offset more than 384 points from where the scene was built.
  • IDs. A box's ID hashes its parent's ID with its sibling index, or with a key the view gives. A box inserted by an if shifts the IDs of the siblings after it, and their state with them, unless they are keyed. immediate.d hashes the call site instead, which needs pushId in loops.
  • Hover covers the box under the pointer and its interactive ancestors, as CSS :hover does, so a row stays hovered while the pointer is over its buttons.
  • Testing. ui.Tester runs a view without a window (clickText, hasText, screenshot), and every app takes --nanoui-snapshot and --nanoui-script. A CPU renderer is the pixel reference the Metal and OpenGL renderers are tested against.
  • Cost. Its benchmark scene closest to the running example builds 1,000 rows of a row box, two formatted labels and a spacer on every frame: 0.32 ms of CPU per frame on an Apple M3 Ultra, for build, layout and paint. immediate.d takes about 1 ms for 1,000 rows on the machine of 11.5. The machines and the text work differ, so only the order of magnitude counts: an arena-backed A2 costs a fraction of the GC-backed one, as finding 2 of 11.5 predicts.
  • Caveats. src/ holds 84,000 lines of Zig written in four weeks: 744 commits since 2026-10-18, 248 of them with a coding agent as co-author. It is 0.x, and a minor release may change the API. On Windows the CPU renderer draws every frame and Direct3D 11 only presents it. Accessibility exists on macOS and iOS only. It also has a webview side with typed IPC, from its start as a port of mygo, which a debugger does not need.

For dentriteui it is a reference design for the immediate islands (A2), not a dependency.

        return;
    }

    {

        {
            continue;
        }

        st.items = st.items.filter!((ref Breakpoint b) => b.enabled != 0).array;
    }

/// Breakpoints panel: plain code over plain data, as in ddui, with real layout.
void breakpointsPanel(Ui ui, ref Breakpoint[] items, string filter)
{
    ui.row(gap: 4, cross: CrossAlign.center)({
        ui.label("Filter");
        ui.expand({ ui.box(height: 20); });
    });
    size_t shown;
    ui.expand({
        ui.column(cross: CrossAlign.stretch)({
            foreach (ref Breakpoint bp; items)
            {
                if (filter.length > 0 && bp.file != filter)
                {
                    continue;
                }
                ++shown;
                ui.pushId(bp.id);
                scope (exit)
                {
                    ui.popId();
                }
                ui.row(gap: 4, cross: CrossAlign.center)({
                    ui.checkbox(bp.enabled, format("%s:%d", bp.file, bp.line));
                    ui.label(format("%d", bp.hits));
                });
            }
        });
    });
    ui.row(gap: 4, cross: CrossAlign.center)({
        ui.label(format("%d of %d shown", shown, items.length));
        ui.expand({ ui.box(); });
        if (ui.button("Remove disabled"))
        {
            Breakpoint[] kept;
            foreach (ref Breakpoint b; items)
            {
                if (b.enabled)
                {
                    kept ~= b;
                }
            }
            items = kept;
        }
    });
}

3.3 Classic retained OOP: WinForms, Qt Widgets, GTK

Model. A tree of long-lived widget objects. You create them once, set properties and attach handlers. The toolkit owns layout (WinForms Dock and Anchor, Qt layouts, GTK boxes), painting and invalidation. Invalidate() adds to the damage region and the next WM_PAINT repaints only that.

State. There are two copies, the application model and the widget properties, and you keep them in sync by hand. Every handler that changes the model must also update every widget showing it. This is the bug farm that both immediate mode and data binding attack.

Update path. A property setter invalidates a rect, the OS coalesces paints, and only damaged areas are painted.

CPU. Proportional to what you change, and zero when idle. Big lists need a virtual mode:

  • WinForms ListView.VirtualMode

3.4 Retained with data binding: WPF/MVVM, Qt QML

Model. Still a retained tree, now declared in markup. Widget properties are bound to view-model properties by name. A binding engine listens for change notifications and copies values, in both directions if asked: INotifyPropertyChanged for objects, ObservableCollection for lists, and ICollectionView.Filter for filtering. MVVM means all state and logic sit in the view model and the view is markup.

Bridge from WinForms. textBox.DataBindings.Add("Text", vm, "Filter"), BindingSource and BindingList<T> already did this, and WinForms already used INotifyPropertyChanged (the WinForms docs describe BindingList<T> turning PropertyChanged into ListChanged). WPF made binding the default.

The gap signals close. A derived property such as Summary needs manual notifications from every place that affects it: the Filter setter and the collection-changed handler, as in the C# below. Forget one and the label goes stale. A signal-based computed records what it read while it ran, so its dependency list maintains itself. WPF bindings with INotifyPropertyChanged are signals with hand-written dependency edges.

QML property bindings are signals in all but name. text: proxy.count + " of " ... is an expression. The engine records which properties it read and "re-evaluates the binding expression and applies the new result" when any of them changes. That is a computed bound to a property by an effect. A plain JavaScript assignment (height = width * 3) silently replaces the binding with a constant, and Qt.binding(function() { ... }) restores it. Delegates receive model roles as required property declarations and write back through model.role = value.

CPU. Per changed property, plus binding-engine overhead: string lookups and reflection in WPF, and the QML engine's expression evaluation.

3.5 Virtual DOM and diffing: React, the Elm architecture

Model. The view is a function of state that returns a description tree. The framework diffs the new description against the previous one and patches the real, retained tree. React components re-run when their state changes. Their hook state belongs to their position: "React preserves a component's state for as long as it's being rendered at its position in the UI tree". Keys make the key part of that position, so list items keep their identity across sorts and deletions.

Elm. One Model, one Msg union, a pure update : Msg -> Model -> Model and a pure view : Model -> Html Msg. The runtime owns the loop. Events become messages, and external events such as debugger hits arrive as messages through subscriptions or ports. Html.Keyed.node gives list children identities.

Update path. A state write or Msg re-runs the affected view functions, which build a new description. The diff patches the real tree, and then layout and paint run.

CPU. Proportional to the re-rendered subtree. One hit-count change re-runs the panel and diffs every visible row unless rows are memoized components. Immediate mode pays the same "re-run the view" cost, but skips the diff and has no second tree.

3.6 Fine-grained signals: SolidJS, Svelte 5 runes, Leptos, Preact signals

Model. Components run once. Solid: "Components, much like other functions, will only run once." The run builds the retained tree. Every dynamic property is bound by an effect that reads signals. When a signal changes, only the effects that read it re-run. There is no component re-render and no diff, except for keyed list reconciliation: Solid's <For> tracks items by reference and moves their nodes, and <Index> tracks by position.

  • Solid: createSignal returns a getter and a setter. Also createMemo, createEffect, and batch, which Solid applies automatically inside effects. untrack, ownership through createRoot ("requires explicit disposal of computations it owns"), and onCleanup.
  • Svelte 5 runes: $state makes deeply reactive proxies. For $derived, Svelte's docs state the algorithm: "Svelte uses something called push-pull reactivity", and derived values "are not re-evaluated until they are actually read". $effect runs "in a microtask after state changes", batched, "after any DOM updates have been applied", and "only depends on the values that it read the last time it ran". The compiler turns the template into effects.
  • Leptos is the same model in Rust: "Components run once, creating (and returning) actual DOM nodes and setting up a reactive system to update those DOM nodes."
  • Preact signals are a standalone library with a version-number algorithm, contrasted in 5.5.

Bridge. This is INotifyPropertyChanged where dependencies are discovered by reading instead of declared by name, and where derived values are first-class nodes that cache and notify.

Update path. A signal write marks dependents, effects flush once per batch, an effect sets a node property, and the node invalidates its layout or paint.

CPU. Proportional to the effects affected. A hit-count change runs one effect and touches one text node. Memory is proportional to the dependency edges (5.4).

3.7 Positional memoization: Jetpack Compose, SwiftUI

Model. The code looks like immediate mode: functions emit UI, with if and for in the body. But the runtime keeps a retained tree and decides what to re-run.

  • Compose. remember { } stores a value at the call's position in the composition (the slot table). Reads of snapshot state (mutableStateOf) are tracked per restart scope and per phase: composition, layout or drawing. Recomposition re-runs only scopes that read changed state, and it "skips functions or lambdas with unchanged parameters". The docs warn that recomposition "is optimistic and may be canceled", and that composables must be side-effect free because they "can execute in any order". Layout is single-pass with constraints ("each node was visited only once").
  • SwiftUI. Views are value structs. "A view forms a dependency on an observable data model object ... when the view's body property reads a property of the object". Unread properties do not cause updates. Identity is structural (position) or explicit (Identifiable, id).

Why this is the natural middle ground for an immediate-mode programmer. You keep the code shape you know, and you get a retained layout tree plus skipping of unchanged subtrees. The price is runtime machinery:

  • a slot table keyed by call position (Compose's compiler plugin generates the keys)
  • stability information so parameters can be compared
  • phase-aware state reads
  • a side-effect API (LaunchedEffect, DisposableEffect, derivedStateOf, which the docs call "expensive")

/// Declares `content` once and reuses its nodes on later frames while `inputs`
/// compare equal, no press lands inside and it handled no input. This is path D.
/// NOTE: re-runs on press only. Hover styling inside would need the same check.
void memo(T)(T inputs, scope void delegate() content,
    string file = __FILE__, size_t line = __LINE__)
{
    Id i = id(file, line);
    Memo!T* slot = memoryFor!(Memo!T)(i, null);
    Memo!T m = *slot;
    if (m !is null && m.inputs == inputs && m.stale == false
        && (pressed && under(m.nodes, mouse)) == false)
    {
        foreach (Node n; m.nodes)
        {
            put(n);
        }
        tracked ~= m.tracked;
        foreach (Id t; m.touched)
        {
            memoryUsed[t] = pass;
        }
        touched ~= m.touched;
        ++skipped;
        return;
    }
    size_t trackedFrom = tracked.length;
    size_t touchedFrom = touched.length;
    bool outerAgain = again;
    again = false;
    Fixed scratch = new Fixed(Size.init);
    pushId(i);
    inside(scratch, content);
    popId();
    Node[] nodes = scratch.children.dup;
    foreach (Node n; nodes)
    {
        put(n);
    }
    if (m is null)
    {
        m = new Memo!T;
        *slot = m;
    }
    m.inputs = inputs;
    m.nodes = nodes;
    m.tracked = tracked[trackedFrom .. $].dup;
    m.touched = touched[touchedFrom .. $].dup;
    m.stale = again;
    again = again || outerAgain;
}

A press inside a cached subtree re-runs it, because widgets poll input while they are declared. A subtree that handled input re-runs in the next build pass, because the click may have changed per-ID memory that the inputs do not cover. The collapsing header in the second memo test is that case. Per-ID memory used inside a skipped subtree is kept alive, as Compose keeps the slots of a skipped group.

Measured in 11.5: with nothing changed, a frame costs about a third of A2's. When everything changed, or on the first frame, it costs 25 to 75% more, because the cache is rebuilt as well. It keeps about 40% more memory than A2 (1.1 against 0.8 KiB per row). Still open: comparing inputs that are not plain values, and changes the cache cannot see, such as a theme switch.

3.8 Native Rust hybrids: what each contributes

gpui (Zed)
Its README: "a hybrid immediate and retained mode, GPU accelerated, UI framework". App state lives in Entitys owned by the app and reached through handles. A change calls cx.notify(), and observers use observe and subscribe/emit. Views implement Render and rebuild a tree of elements, which is laid out with Taffy (gpui/src/taffy.rs) and painted. uniform_list and list virtualize. Actions turn keystrokes into typed structs. Idea: retained state with explicit invalidation, plus a per-frame element tree with real layout. That is path A2.
Makepad
Retained widgets, drawn by walking the tree again on every redraw. A widget is a Rust struct with handle_event and draw_walk. Its look and layout come from Splash, Makepad's own script language, which reloads live while the app keeps its state. Every look is a shader in the same language: a button's background is a pixel function that draws signed distance fields. Read on main at 506ec05:
  • Layout happens inside the draw walk. A "turtle" places each child as it draws, so a Fit size is known only after the children drew. Centring and end alignment are applied afterwards, by adding an offset to instances already written to the GPU buffers (move_align_list in draw/src/turtle.rs). That is one pass and no layout tree. The price: a parent cannot ask a Fit child for its width without drawing it (Widget::measure_width answers None), and Splash's guide calls a missing height: Fit the "most common failure mode".
  • Repaint boundaries are cached draw lists. A view with its own draw list keeps the last draw's instances. The walk skips it unless a widget inside called redraw(cx) or its rect or clip moved (begin_maybe, Cx2d::will_redraw).
  • Input is tested against the last draw's rects, as in A2: event.hits(cx, self.draw_bg.area()) reports hover, press and release on the rect the widget drew. Widgets emit actions, and app code polls them: self.ui.button(cx, ids!(increment_button)).clicked(actions).
  • Lists are immediate loops inside the retained tree. draw_walk returns a DrawStep, which can pause at a child. The app's widget resumes the walk until it stops at the PortalList, then loops over the visible items. Each item fills a pooled widget made from a template and draws it (the snippet below).
  • Batching by shader costs draw order. Instances of one shader share a draw call, so text can end up under a background drawn after it. Splash's guide makes new_batch: true "required on any container with show_bg: true that contains text children".
  • One semantic tree (libs/a11y, no dependencies) is built while drawing. A node's ID is the widget's ID plus a part index, and changes go out as diffs. Screen-reader adapters, UI tests (app.locator(Selector::id("increment_button")).click()) and automation all read it. 4.4 Events, commands, undo/redo

Three layers, each doing one job:

  1. Widget events. In A2 they are return values (if (ui.button(...))). In B they are delegates (onClick). Both are local and synchronous.
  2. Messages (SumType) for anything app-level: menus, keybindings, the command palette, scripting and tests all produce the same Msg values. Being data, they can be logged, replayed and remapped. gpui's typed actions are the same idea.
  3. Commands for edits: objects with apply, revert, label and merge, kept in a history. Debugger control messages (step, continue) are messages but not commands, because they are not undoable.

4.5 Lists: keys and virtualization

Identity

Retained lists need reconciliation. Match new items to existing rows by key, reuse what survives, create new rows, and dispose the rest, along with their owner scopes:

/// Reuses rows whose key survives, builds new ones, disposes the rest.
void update(T[] items)
{
    R[] next;
    bool[K] keep;
    foreach (T item; items)
    {
        K k = keyOf(item);
        keep[k] = true;
        if (R* found = k in rows)
        {
            next ~= *found;
            continue;
        }
        R made;
        runWithOwner(owner, () {
            scopes[k] = effectScope(() { made = make(item); });
        });
        rows[k] = made;
        next ~= made;
        ++created;
    }
    foreach (K k; rows.keys)
    {
        if ((k in keep) is null)
        {
            scopes[k].dispose();
            scopes.remove(k);
            rows.remove(k);
            ++disposed;
        }
    }
    ordered = next;
}

Immediate lists need only stable IDs. Scope widget IDs by the item key (ui.pushId(bp.id)), never by row index and never by memory address (the ddui finding in 3.2.3).

Virtualization for 100k+ rows

Fixed-height rows (memory, register dumps) are arithmetic:

/// Rows overlapping the viewport, widened by `overscan` rows on each side.
RowRange visibleFixed(double scrollY, double viewH, double rowH, size_t count, size_t overscan = 2)
{
    if (count == 0)
    {
        return RowRange.init;
    }
    size_t first = cast(size_t) floor(max(0.0, scrollY) / rowH);
    size_t last = cast(size_t) floor((max(0.0, scrollY) + viewH) / rowH) + 1;
    first = first > overscan ? first - overscan : 0;
    last = min(count, last + overscan);
    return RowRange(min(first, count), last);
}

Variable-height rows (logs with wrapping, source with folded regions) need prefix sums. A Fenwick tree gives O(log n) row-to-offset and offset-to-row, unmeasured rows use an estimate, and appends are O(log n) for logs:

/// Row containing content position `y`, clamped to the last row.
size_t indexAt(double y) const
{
    size_t n = heights.length;
    size_t step = 1;
    while (step * 2 <= n)
    {
        step *= 2;
    }
    size_t pos;
    double rest = y;
    for (; step > 0; step /= 2)
    {
        if (pos + step <= n && tree[pos + step] <= rest)
        {
            pos += step;
            rest -= tree[pos];
        }
    }
    return n == 0 ? 0 : min(pos, n - 1);
}

When rows above the viewport get measured and change height, keep the scroll position relative to an anchor row, or the view jumps:

/// Anchor for the row at the top of the viewport.
Anchor capture(const RowHeights rows, double scrollY)
{
    size_t r = rows.indexAt(scrollY);
    return Anchor(r, scrollY - rows.offsetOf(r));
}
/// Scroll position that puts the anchor back where it was.
double restore(const RowHeights rows, Anchor a)
{
    return rows.offsetOf(a.row) + a.delta;
}
  • Memory view: 16 bytes per row and fixed height, so row = (address - base) / 16. Already a toy in hybrid.d (30 rows built out of 65,536).
  • Disassembly: fixed height, but instruction lengths vary, so address-to-row needs an index of instruction starts, built lazily per region and invalidated on code patches. Key rows and the selection by address, never by row number. Scrolling backwards needs a resync heuristic (decode from a known boundary, such as a symbol start).
  • Logs and console: append-only, variable height when wrapped. Use RowHeights.append plus "stick to bottom" when the view is at the end, and select by sequence number.
  • Retained virtualization (path B): keep a pool of row nodes for the visible window, as GTK's factories, Compose's LazyColumn and Flutter's builders do. Each pooled row reads item(indexSignal.get), so scrolling only writes the index signals of rows that changed item. Makepad fills its pooled rows from an immediate loop over the visible items instead (3.8).
  • Immediate virtualization (A2): the list must know its viewport when it declares rows. Either use last frame's rect (one-frame lag on resize) or give the list a callback that the layout pass calls with the visible range, as gpui's uniform_list and Compose's LazyColumn do. Use the callback.

4.7 Memory

  • When it matters. D's GC stops the world and runs when an allocation finds no free memory. Steady per-frame garbage is the risk, not the GC itself. A retained tree allocates on change only. An immediate library that allocates a tree, closures and formatted strings every frame produces garbage at frame rate.
  • B: nodes, effects and Links are GC objects, allocated when the tree changes and not per frame. A Link is 56 bytes on 64-bit (a uint plus six references), placed in a 64-byte GC bin. A panel.d row costs one scope, two effects and about four links. Measured, B keeps 1.2 MiB at 1,000 rows, model included, and building them leaves about 1.4 KiB of garbage per row (11.5). 100k live rows would keep over 100 MiB, which is one more reason to virtualize and pool rows.
  • Islands (A2): allocate per-frame nodes from a frame arena that is reset in begin(). Use scope delegates (no closure allocation), and format into a per-frame text arena (sformat into a buffer), as ddui's text_stack does. immediate.d uses new for brevity, and that is the first thing a real version changes.
  • @nogc hot paths: tessellation, glyph lookup, command emission and hit testing. They run every frame and need no GC, so make them @nogc nothrow over preallocated buffers. render.d appends to dynamic arrays for clarity and would be changed.
  • Big fixed buffers: ddui's mu_create uses malloc, so the GC never scans its 392 KiB context. Keep doing that for atlases, vertex buffers and arenas.
  • Measure before tuning: --DRT-gcopt=profile:1 prints collection counts and pause times.

4.8 Threading

The debugger backend runs on its own thread (ptrace or the Windows debug API block). It must never touch UI state. It posts into mailboxes and wakes the UI loop. The UI thread drains once per frame and applies everything in one batch.

/// Latest-value-wins updates keyed by `K`.
final class Mailbox(K, V)
{
    private Mutex lock;               /// guards `pending`
    private V[K] pending;             /// newest value per key since the last drain
    private void delegate() nothrow wake; /// called when the box goes from empty to non-empty

    /// Creates a box that calls `wake` from the posting thread.
    this(void delegate() nothrow wake)
    {
        lock = new Mutex;
        this.wake = wake;
    }

    /// Records `value` for `key`, replacing any undrained value. Any thread.
    void post(K key, V value)
    {
        bool first;
        lock.lock();
        first = pending.length == 0;
        pending[key] = value;
        lock.unlock();
        if (first)
        {
            wake();
        }
    }

    /// Takes everything posted since the last drain. UI thread.
    V[K] drain()
    {
        lock.lock();
        V[K] taken = pending;
        pending = null;
        lock.unlock();
        return taken;
    }
}
/// 100k hit updates from a backend thread become one batch and one effect run per breakpoint.
unittest
{
    import core.atomic : atomicLoad, atomicOp;
    import core.thread : Thread;
    import signals;

    shared int wakes;
    Mailbox!(uint, uint) hits = new Mailbox!(uint, uint)(() nothrow { atomicOp!"+="(wakes, 1); });
    Queue!string log = new Queue!string(() nothrow { atomicOp!"+="(wakes, 1); });

    /// Effect counting runs of `s` into `runs[key]`.
    /// NOTE: closures made directly in a loop body share one frame, so each
    /// effect is created in its own call.
    static void watch(Signal!uint s, int[] runs, uint key)
    {
        effect(() {
            s.get;
            ++runs[key];
        });
    }

    Signal!uint[uint] hitSignals;
    int[] runs = new int[5];
    foreach (uint id; 1 .. 5)
    {
        hitSignals[id] = signal(0u);
        watch(hitSignals[id], runs, id);
    }

    Thread backend = new Thread(() {
        foreach (uint n; 1 .. 100_001)
        {
            hits.post(n % 4 + 1, n);
            if (n % 25_000 == 0)
            {
                log.post("stopped at checkpoint");
            }
        }
    });
    backend.start();
    backend.join();

    assert(atomicLoad(wakes) == 2, "one wake per box, the UI had not drained yet");
    uint[uint] latest = hits.drain();
    batch(() {
        foreach (uint id, uint value; latest)
        {
            hitSignals[id].set(value);
        }
    });
    assert(hitSignals[1].peek == 100_000);
    assert(hitSignals[2].peek == 99_997);
    foreach (uint id; 1 .. 5)
    {
        assert(runs[id] == 2, "initial run plus one");
    }
    assert(log.drain().length == 4);
    assert(hits.drain().length == 0);
}
  • Coalesce what is "latest value": hit counts, registers, thread states. 100k posts become four signal writes and one effect run per breakpoint.
  • Keep order where it matters: log lines and stop events go through Queue.
  • Wake: SDL's SDL_PushEvent with a user event breaks SDL_WaitEvent. egui's request_repaint works from any thread. The wake runs on the posting thread, so it must be cheap and thread-safe.
  • B: applying a batch is batch(() { ... set ... }). Islands (A2): it is plain assignment followed by requestFrame().
  • signals.d's graph state is thread-local by D's default. A write from the backend thread would see an empty tracking context and its own empty effect queue, so UI effects would silently never run. The mailbox is the only door.
  • Long jobs (symbol loading, disassembling a region, source indexing) run on worker threads and post results the same way. std.concurrency also works for typed messages, but the UI loop still needs a wake.

D details, checked with ldc2 1.40 and dmd 2.110:

  • UFCS makes a component from another module look built in. ui.button(variant: Variant.danger)({ ... }) calls the free function widgets.button.button(ui, ...). Named arguments work through UFCS, and the __LINE__ default sees the caller's line, so IDs work as they do for built-ins.
  • A Ui member hides every free function of the same name. With a member bool button(string), the call above fails with "no parameter named `variant`", because UFCS is only tried when member lookup finds nothing. So Ui holds primitives only, and its own widgets are free functions too. immediate.d now works that way.
  • A module named button hides the function button from its importers: "function expected before `()`, not `module button`". Components go in a package, here widgets.button, later dentrite.widgets.button.
  • Two imported modules that both define button for Ui never silently pick one. A call both accept fails with "`button` matches conflicting symbols". A call only one accepts, such as one passing enabled:, resolves. A module's own declarations win over its imports, which is why the tests in widgets/button.d reach its button and not immediate.d's. An app that imports both picks one with a selective import.
  • static import turns UFCS off for that module's functions, and a module-level selective import of row hides every other row in the importing module. bench.d has both problems with layout.d's row and column, so it imports the widgets by name inside the one function that uses them.

/// Sets the fields of `s` named by the entries of `sec`. Throws on an unknown field or a bad value.
void apply(T)(ref T s, const Section sec, const Color[string] palette, string file)
{
    foreach (ref const Entry e; sec.entries)
    {
        bool known;
        static foreach (string name; FieldNameTuple!T)
        {
            if (e.key == name)
            {
                known = true;
                alias F = typeof(__traits(getMember, s, name));
                static if (is(F == Color))
                {
                    __traits(getMember, s, name) = colorOf(e, palette, file);
                }
                else
                {
                    try
                    {
                        __traits(getMember, s, name) = to!F(e.value);
                    }
                    catch (ConvException)
                    {
                        throw new Exception(format("%s(%d): %s is not a %s", file, e.line, e.value, F.stringof));
                    }
                }
            }
        }
        if (known == false)
        {
            throw new Exception(format("%s(%d): %s has no field %s", file, e.line, T.stringof, e.key));
        }
    }
}

No DSL for content or behaviour. Content is already declarative: named options and a slot read like markup, and they keep D's control flow, types and IDE support. Cost. Measured on A2 and D (11.5), the whole change keeps timings within the run-to-run spread and adds up to 5% garbage per frame, under 2% in most cases. Most of that is the color in every draw command: Drawn grew from 32 to 40 bytes. A first attempt stored the text color in every label instead. Open issue. memo (path D) re-runs a subtree on a press inside it, not on hover. A hover-styled button inside memo keeps its old fill until something else re-runs it. D would need the pointer's position over the subtree as one more input.

Recommendation. B: one module per component, in a package. A component is a function returning a node. Content is a slot (child nodes), look is a style struct loaded from theme files and inherited down the tree, and behaviour comes from shared pointer and focus handlers. Islands (A2): the same split over public primitives of Ui, as widgets/button.d does. Ui has no widget members, and the built-in widgets are components like any other. Content is a slot delegate, and behaviour is a few core primitives shared by every component. Both: one theme file and one style struct per component, so a button looks the same in the tree and in an island. 5. Signals deep dive

5.1 Push, pull, push-pull

Push (eager)
A write recomputes dependents immediately. It is simple, but it does work for values nobody reads, and without careful ordering it shows glitches (5.2).
Pull (lazy)
A write only does bookkeeping, such as bumping a version number. Reads check whether inputs changed and recompute then. No wasted work, but every read validates its chain, and effects still need some kind of notification. Preact signals are pull-validated with version numbers.
Push-pull
A write pushes cheap invalidation marks down the graph and queues the effects it reaches. No user code runs during the push. When the queued effects run, their reads pull: only nodes whose inputs really changed are recomputed. Svelte 5's docs say it directly ("push-pull reactivity", derived values "are not re-evaluated until they are actually read"). alien-signals and Reactively work this way.

5.2 The diamond problem and glitches

        a            b = a + 1
       / \           c = a * 10
      b   c          d = b + c
       \ /
        d ---> effect: print(d)

a: 1 -> 2
naive push: b = 3, d = 3 + 10 = 13 (c still old!), c = 20, d = 23
            the effect prints 13, a value that never existed: a glitch
push-pull:  mark b, c, d pending, queue the effect. The effect reads d,
            d checks b (recomputes 3, changed), recomputes itself, reads c
            (pending, recomputes 20): d = 23, printed once

Glitch freedom, in Reactively's words: "Never allow user code to see intermediate state where only some reactive elements have updated." Pure push avoids glitches only by recomputing in topological order (heights). Push-pull gets it for free, because nothing runs until a reader pulls, and a pull recomputes inputs first.

/// Diamond: a feeds b and c, d reads both. One write, one run of d, no torn reads.
unittest
{
    Signal!int a = signal(1);
    int bRuns, cRuns, dRuns;
    Computed!int b = computed(() { ++bRuns; return a.get + 1; });
    Computed!int c = computed(() { ++cRuns; return a.get * 10; });
    Computed!int d = computed(() { ++dRuns; return b.get + c.get; });
    int[] seen;
    effect(() { seen ~= d.get; });
    assert(seen == [12]);
    a.set(2);
    assert(seen == [12, 23]);
    assert(bRuns == 2 && cRuns == 2 && dRuns == 2);
}

5.3 Coloring, batching, untracked reads, conditional dependencies, cleanup, memory

  • Coloring. alien-signals uses two marks. Pending means "some upstream node changed, I may be stale". Dirty means "a direct dependency changed value, I am stale". A write marks the signal Dirty and everything reachable Pending. A Pending node that is read runs checkDirty: it walks its dependencies and refreshes the Dirty ones. If any value really changed, shallowPropagate promotes the direct subscribers to Dirty. If nothing changed, it clears Pending without running user code. Reactively's three colors (clean, check, dirty) are the same idea.
  • Batching. A batch depth counter defers the flush. Signals keep a pending and a current value, so a write followed by a revert in one batch commits nothing and runs nothing.
  • Untracked reads clear the active subscriber for the duration of the read (untracked), or read the raw value (peek).
  • Conditional dependencies. Every run re-tracks. link reuses the existing edge when dependencies come in the same order as last time (a cursor, depsTail), and purgeDeps unlinks whatever the run did not read. A branch not taken stops being a dependency.
  • Cleanup and ownership. Effects and scopes link to their owner just like a dependency. Disposing an owner unlinks its children, which fires their unwatched hook and disposes them. Re-running an effect first disposes the children its previous run created.
  • Memory. One Link per edge (56 bytes in D on 64-bit) plus one object per node. A computed whose last reader goes away unlinks from its sources, so whole subgraphs become garbage. A computed read only outside any effect stays subscribed to its sources. That is alien-signals behaviour, kept here. Preact avoids it by not tracking unobserved computeds.
/// Batching: several writes, one run. Write then revert inside a batch, no run.

    assert(subscriberCount(mid) == 0);
    assert(subscriberCount(src) == 0, "mid unsubscribed from src");
    assert(mid.get == 2, "still readable, recomputed on demand");
}

5.4 How alien-signals works

alien-signals (stackblitz, v3.2.1, read at 113f581) is "a push-pull based signal algorithm". Its README credits Vue 3's propagation, Preact's doubly linked lists, Svelte's inner-effect scheduling and Reactively's graph coloring. It imposes constraints on its core: no Array, Set or Map, and no recursion. The core was ported back into Vue 3.6. Its pieces:

  1. Edges are objects in two lists at once. A Link sits in its subscriber's dependency list and in its dependency's subscriber list, both doubly linked. Adding, removing and reusing an edge is O(1), with no hash sets.
  2. link reuses edges in order. A run resets depsTail to null. Each read checks whether the next existing edge is the same dependency. If so it advances the cursor, otherwise it inserts. After the run, everything past the cursor is purged. A steady-state re-run therefore allocates nothing.
  3. propagate walks subscribers iteratively with an explicit stack, marks them Pending, recurses into mutable nodes (computeds) and queues watching effects. Two extra bits handle writes made while an effect runs: RecursedCheck ("running") and Recursed ("written during my run").
  4. checkDirty walks up through Pending dependencies, also iteratively, and refreshes Dirty computeds and signals on the way.
  5. The effect queue runs outer effects before inner ones: notify also queues watching parents and reverses the inserted run. An outer effect that re-runs may dispose an inner one before it runs.
  6. Unobserved computeds drop their dependencies (unwatched), and an effect dropped by its owner disposes itself the same way.
/// Edge between a dependency and a subscriber, threaded through both nodes' lists.
struct Link
{
    uint cycle;          /// run counter when last confirmed
    ReactiveNode dep;    /// node being read
    ReactiveNode sub;    /// node reading it
    Link* prevSub;       /// previous subscriber of `dep`
    Link* nextSub;       /// next subscriber of `dep`
    Link* prevDep;       /// previous dependency of `sub`
    Link* nextDep;       /// next dependency of `sub`
}
/// Records that `sub` read `dep`, reusing the existing link when the order is unchanged.
private void link(ReactiveNode dep, ReactiveNode sub, uint version_)
{
    Link* prevDep = sub.depsTail;
    if (prevDep !is null && prevDep.dep is dep)
    {
        return;
    }
    Link* nextDep = prevDep !is null ? prevDep.nextDep : sub.deps;
    if (nextDep !is null && nextDep.dep is dep)
    {
        nextDep.cycle = version_;
        sub.depsTail = nextDep;
        return;
    }
    Link* prevSub = dep.subsTail;
    if (prevSub !is null && prevSub.cycle == version_ && prevSub.sub is sub)
    {
        return;
    }
    Link* l = new Link(version_, dep, sub, prevSub, null, prevDep, nextDep);
    sub.depsTail = l;
    dep.subsTail = l;
    if (nextDep !is null)
    {
        nextDep.prevDep = l;
    }
    if (prevDep !is null)
    {
        prevDep.nextDep = l;
    }
    else
    {
        sub.deps = l;
    }
    if (prevSub !is null)
    {
        prevSub.nextSub = l;
    }
    else
    {
        dep.subs = l;
    }
}
/// Marks everything downstream of `l` pending and queues reached effects.
private void propagate(Link* l, bool innerWrite)
{
    Link* next = l.nextSub;
    Link*[] stack;
    top: while (true)
    {
        ReactiveNode sub = l.sub;
        uint f = sub.flags;
        if ((f & (Flag.recursedCheck | Flag.recursed | Flag.dirty | Flag.pending)) == 0)
        {
            sub.flags = f | Flag.pending;
            if (innerWrite)
            {
                sub.flags |= Flag.recursed;
            }
        }
        else if ((f & (Flag.recursedCheck | Flag.recursed)) == 0)
        {
            f = Flag.none;
        }
        else if ((f & Flag.recursedCheck) == 0)
        {
            sub.flags = (f & ~Flag.recursed) | Flag.pending;
        }
        else if ((f & (Flag.dirty | Flag.pending)) == 0 && isValidLink(l, sub))
        {
            sub.flags = f | Flag.recursed | Flag.pending;
            f &= Flag.mutable;
        }
        else
        {
            f = Flag.none;
        }

        if ((f & Flag.watching) != 0)
        {
            notify(sub);
        }

        if ((f & Flag.mutable) != 0 && sub.subs !is null)
        {
            l = sub.subs;
            if (l.nextSub !is null)
            {
                stack ~= next;
                next = l.nextSub;
            }
            continue;
        }

        if (next !is null)
        {
            l = next;
            next = l.nextSub;
            continue;
        }

        while (stack.length > 0)
        {
            l = stack[$ - 1];
            stack.length -= 1;
            if (l !is null)
            {
                next = l.nextSub;
                continue top;
            }
        }
        break;
    }
}
/// Walks pending dependencies of `sub`, recomputing as needed, true if `sub` must re-run.
private bool checkDirty(Link* l, ReactiveNode sub)
{
    Link*[] stack;
    int depth;
    bool dirty;
    top: while (true)
    {
        ReactiveNode dep = l.dep;
        uint f = dep.flags;
        if ((sub.flags & Flag.dirty) != 0)
        {
            dirty = true;
        }
        else if ((f & (Flag.mutable | Flag.dirty)) == (Flag.mutable | Flag.dirty))
        {
            Link* depSubs = dep.subs;
            if (dep.refresh())
            {
                if (depSubs.nextSub !is null)
                {
                    shallowPropagate(depSubs);
                }
                dirty = true;
            }
        }
        else if ((f & (Flag.mutable | Flag.pending)) == (Flag.mutable | Flag.pending))
        {
            stack ~= l;
            l = dep.deps;
            sub = dep;
            ++depth;
            continue;
        }

        if (dirty == false && l.nextDep !is null)
        {
            l = l.nextDep;
            continue;
        }

        while (depth-- > 0)
        {
            l = stack[$ - 1];
            stack.length -= 1;
            if (dirty)
            {
                Link* subSubs = sub.subs;
                if (sub.refresh())
                {
                    if (subSubs.nextSub !is null)
                    {
                        shallowPropagate(subSubs);
                    }
                    sub = l.sub;
                    continue;
                }
                dirty = false;
            }
            else
            {
                sub.flags &= ~Flag.pending;
            }
            sub = l.sub;
            if (l.nextDep !is null)
            {
                l = l.nextDep;
                continue top;
            }
        }
        break;
    }
    return dirty && sub.flags != 0;
}

5.5 How Preact's version counters differ

Preact signals (read at 8d5e9b7) store versions rather than marks. Each source has a _version, bumped when its value changes. Each edge node remembers "the version number of the source that target has last seen". On read, a computed:

  • returns at once if the global version has not moved since it last validated (_globalVersion === globalVersion)
  • otherwise walks its sources in order, refreshing each, and recomputes on the first version mismatch (needsToRecompute)

Computeds with no subscribers do not subscribe upstream (no TRACKING flag). They are validated on read through the global version. Edge nodes are recycled between runs (version -1 marks "maybe unused").

5.6 The D implementation

examples/signals.d ports alien-signals 3.2's algorithm (system.ts and the operator functions in index.ts). Differences from the original:

  • Tracking and ownership are separate, as in Solid (its Owner and Listener). activeSub collects dependencies and currentOwner adopts new effects and scopes. Scope bodies and untracked blocks own without tracking. In alien-signals the running node does both, so a signal read directly in an effectScope body becomes a dependency of the scope.
  • runWithOwner creates row scopes under a long-lived list owner, so re-running the list effect does not dispose rows that survive (panel.d).
  • onCleanup registers on the current owner instead of the effect returning a cleanup function. Several cleanups per effect are allowed and run last first.
  • Nodes are classes, and edges are GC-allocated Link structs. Graph globals are thread-local, which D gives by default.
  • Equality: classes compare with !is, everything else with !=. Arrays therefore compare by content, which saves downstream work but costs a walk, and NaN always counts as changed.
/// Writable reactive value.
final class Signal(T) : ReactiveNode
{
    private T current; /// value seen by readers
    private T pending; /// last written value

    /// Creates a signal holding `value`.
    this(T value)
    {
        current = value;
        pending = value;
        flags = Flag.mutable;
    }

    /// Value, tracked by the running effect or computed.
    T get()
    {
        if ((flags & Flag.dirty) != 0)
        {
            if (refresh() && subs !is null)
            {
                shallowPropagate(subs);
            }
        }
        if (activeSub !is null)
        {
            link(this, activeSub, cycle);
        }
        return current;
    }

    /// Latest written value, untracked.
    T peek()
    {
        return pending;
    }

    /// Writes `value` and runs affected effects unless batching.
    void set(T value)
    {
        if (changed(pending, value) == false)
        {
            return;
        }
        pending = value;
        flags = Flag.mutable | Flag.dirty;
        if (subs !is null)
        {
            propagate(subs, runDepth > 0);
            if (batchDepth == 0)
            {
                flush();
            }
        }
    }

    /// Commits the pending value, true if it differs from the committed one.
    protected override bool refresh()
    {
        flags = Flag.mutable;
        T old = current;
        current = pending;
        return changed(old, current);
    }
}
/// Value, recomputed first if a dependency changed.
T get()
{
    uint f = flags;
    if ((f & Flag.dirty) != 0
        || ((f & Flag.pending) != 0 && checkDirty(deps, this)))
    {
        if (refresh() && subs !is null)
        {
            shallowPropagate(subs);
        }
    }
    else if ((f & Flag.pending) != 0)
    {
        flags = f & ~Flag.pending;
    }
    else if (f == 0)
    {
        refresh();
    }
    if (activeSub !is null)
    {
        link(this, activeSub, cycle);
    }
    return value;
}
/// Creates an effect owned by the current owner and runs it once.
Effect effect(void delegate() fn)
{
    Effect e = new Effect(fn);
    adopt(e);
    e.execute();
    return e;
}
/// Runs `e` if it is dirty, or if a pending check finds a changed dependency.
private void run(Effect e)
{
    uint f = e.flags;
    if ((f & Flag.dirty) != 0
        || ((f & Flag.pending) != 0 && checkDirty(e.deps, e)))
    {
        if ((f & Flag.hasChildEffect) != 0)
        {
            disposeChildren(e);
        }
        if (e.cleanups.length > 0)
        {
            runCleanups(e.cleanups);
            if (e.disposed)
            {
                return;
            }
        }
        e.execute();
    }
    else if (e.deps !is null)
    {
        e.flags = Flag.watching | (f & Flag.hasChildEffect);
    }
}

6.2 Recommendation: box constraints

  • One pass and O(n), with no pathological cases unless intrinsics are used.
  • Caching and relayout boundaries fall out of the protocol (6.4). They matter in path B and are harmless in A2.
  • Small enough to own. Row, Column, Flexible, Padding, Stack, Align, Wrap and a scroll view cover a debugger.
  • The same protocol serves a retained tree (B) and a per-frame tree (A2). Prototyping it is not wasted whichever path wins.
  • Flexbox's extra power (wrap with shrink, grid, min-content) costs a large semantic surface. If a grid is ever needed, Taffy's CSS Grid can be ported later behind the same layout(Constraints) call.

6.3 The D protocol

/// Allowed size range handed from parent to child.
struct Constraints
{
    float minW = 0;               /// smallest allowed width
    float maxW = float.infinity;  /// largest allowed width
    float minH = 0;               /// smallest allowed height
    float maxH = float.infinity;  /// largest allowed height

    /// Exactly `s`.
    static Constraints tight(Size s)
    {
        return Constraints(s.w, s.w, s.h, s.h);
    }

    /// Anything from zero up to `s`.
    static Constraints loose(Size s)
    {
        return Constraints(0, s.w, 0, s.h);
    }

    /// True if only one size satisfies the constraints.
    bool isTight() const
    {
        return minW == maxW && minH == maxH;
    }

    /// `s` clamped into range.
    Size constrain(Size s) const
    {
        return Size(clamp(s.w, minW, maxW), clamp(s.h, minH, maxH));
    }

    /// Constraints shrunk by `i`, never below zero.
    Constraints deflate(Insets i) const
    {
        float dx = i.left + i.right;
        float dy = i.top + i.bottom;
        return Constraints(max(0f, minW - dx), max(0f, maxW - dx),
            max(0f, minH - dy), max(0f, maxH - dy));
    }
}
/// Lays out under `c`, skipping work when clean and `c` is unchanged.
final Size layout(Constraints c, bool parentUsesSize = true)
{
    boundary = parentUsesSize == false || c.isTight || parent is null;
    if (needsLayout == false && c == constraints)
    {
        return size;
    }
    constraints = c;
    this.parentUsesSize = parentUsesSize;
    size = c.constrain(performLayout(c));
    needsLayout = false;
    ++layoutRuns;
    return size;
}
/// Lays out the child in the deflated space and offsets it.
protected override Size performLayout(Constraints c)
{
    Node child = children[0];
    Size s = child.layout(c.deflate(insets));
    child.offset = Point(insets.left, insets.top);
    return Size(s.w + insets.left + insets.right, s.h + insets.top + insets.bottom);
}
/// Inflexible children first, then flex shares of what is left, then positions.
protected override Size performLayout(Constraints c)
{
    float mainMax = axis == Axis.horizontal ? c.maxW : c.maxH;
    float crossMax = axis == Axis.horizontal ? c.maxH : c.maxW;
    bool stretch = cross == CrossAlign.stretch && isInfinity(crossMax) == false;
    float crossMin = stretch ? crossMax : 0;

    float used = children.length > 1 ? gap * (children.length - 1) : 0;
    float crossSize = 0;
    int totalFlex;
    foreach (Node k; children)
    {
        Flexible f = cast(Flexible) k;
        if (f !is null && f.flex > 0)
        {
            totalFlex += f.flex;
            continue;
        }
        Size s = k.layout(make(0, float.infinity, crossMin, crossMax));
        used += mainOf(s);
        crossSize = max(crossSize, crossOf(s));
    }

    bool bounded = isInfinity(mainMax) == false;
    float free = bounded ? max(0f, mainMax - used) : 0;
    float perFlex = totalFlex > 0 ? free / totalFlex : 0;
    foreach (Node k; children)
    {
        Flexible f = cast(Flexible) k;
        if (f is null || f.flex <= 0)
        {
            continue;
        }
        float share = perFlex * f.flex;
        Size s = k.layout(make(f.tight ? share : 0, share, crossMin, crossMax));
        used += mainOf(s);
        crossSize = max(crossSize, crossOf(s));
    }

    float mainSize = bounded ? mainMax : used;
    if (stretch)
    {
        crossSize = crossMax;
    }

    float pos = 0;
    foreach (Node k; children)
    {
        float slack = crossSize - crossOf(k.size);
        float across = cross == CrossAlign.center ? slack / 2 : 0;
        k.offset = axis == Axis.horizontal ? Point(pos, across) : Point(across, pos);
        pos += mainOf(k.size) + gap;
    }
    return axis == Axis.horizontal ? Size(mainSize, crossSize) : Size(crossSize, mainSize);
}

6.4 Measurement caching and relayout boundaries

A node skips work when it is clean and gets the same constraints as last time. A change marks the node and walks up until it reaches a relayout boundary, a node whose size cannot change as a result. Flutter's rule, from RenderObject.layout:

_isRelayoutBoundary = !parentUsesSize || sizedByParent || constraints.isTight || parent == null;

The owner relayouts boundaries parents-first, with their last constraints. The test below changes the summary text and checks that only the outer column, the footer row and the flexible spacer redo work. Then it changes text inside the list, which has tight constraints, and checks that the outer column is untouched.

6.5 Deferred layout for immediate mode (path A2)

The immediate-mode layout paradox, from egui's README: "to know the size of the window, we must do the layout, but the layout code also checks for interaction ... and so it needs to know the window position before showing the window contents." egui resolves it with remembered sizes and discard passes, and microui with a settle frame. Clay, gpui and nanoui (3.2.5) resolve it differently, and so do dentriteui's immediate islands (9):

  1. Declare the frame's tree. Widget calls create nodes and return interaction results.
  2. Answer interaction from last frame's rects, looked up by ID. This is not a hack: the user clicked on the previous frame, so its rects are the ones that match what they saw. Clay does this in Clay_SetPointerState. gpui does it in Window::dispatch_mouse_event, which hit-tests self.rendered_frame and runs that frame's listeners. gpui delivers results as callbacks, while A2, like Clay_Hovered and nanoui, returns them from the widget call.
  3. Lay out the whole tree with box constraints at the end of frame(), then paint. Layout is exact on every frame, including the first.

  • Responsive decisions ("if wide, show the bytes column") can read last frame's rect for the ID, with a one-frame lag on resize, or use a layout-time builder like Flutter's LayoutBuilder.
  • Custom painting (hex grid, disassembly arrows, plots) gets a paint callback with the final rect, like gpui's canvas or egui's painter.
  • Cost: a node per element per frame, a layout pass and a paint pass. Measured in 11.5: about 1 µs per declared row, most of it GC allocation. nanoui's arena-backed core builds, lays out and paints a similar 1,000-row scene in 0.32 ms (3.2.5).
  • Interaction timing: a change made after part of the view was declared would show only on the next frame. egui and ddui accept that and ask for another frame. nanoui declares the view again before layout while a pass handled input, at most four passes, with the press spent after the first. Ui.frame in immediate.d does the same, so a drawn frame never shows the state from before the click. The cost is a second declaration on frames that handle input.
  • Scrolling: an event that only moved a scroll offset can shift the last frame's draw list and rects instead of declaring, laying out and painting, as nanoui's retain.zig does.

7. Rendering and polish

7.1 What makes egui and Rerun look good

  • Text. epaint in egui 0.37 parses fonts with skrifa, shapes with harfrust and rasterizes glyphs with vello_cpu. Hinting is on by default. "Sub-pixel binning renders each glyph at up to four fractional horizontal offsets, giving more even kerning", and it is "always disabled for CJK characters". Shaped text is cached per LayoutJob. Rerun picks Inter for UI text and JetBrains Mono for code.
  • Atlas. Glyphs are rasterized on demand into one texture atlas (2048 px maximum side by default), keyed by glyph, size and subpixel bin. The same texture holds a white texel (WHITE_UV), so untextured shapes and text share a texture and batch into few draw calls.
  • Anti-aliasing by feathering. "Feathering works by making each edge into a thin gradient into transparency", 1 physical pixel by default. No MSAA, no shader tricks, and it works on any backend that can blend textured triangles.
  • Shapes. Rects with corner radii, circles, ellipses, paths, strokes, Bézier curves. A shadow is a RectShape with blur_width: a very wide feather.
  • Spacing and tokens. egui has a Spacing style (item spacing, button padding, interact size). Rerun layers design tokens on top: sizes such as large_button_size: 22 and large_button_corner_radius: 6, and a color table of hue scales, in RON files for light and dark.
  • Icons. Rerun ships 129 SVG icons drawn for small sizes and rasterized at the needed scale.
  • DPI. egui works in logical points with pixels_per_point. Text shapes "need to be recreated if pixels_per_point (dpi scale) changes", and text is rounded to pixels by default.
  • Animation. ctx.animate_bool and animate_value_with_time are immediate-mode friendly, keyed by ID and requesting repaints while running. Rerun has a motion module and a 0.2 s slow animation token.

By contrast, ddui today has integer rects, a baked 128x128 ASCII bitmap font, no anti-aliasing and solid fills. Everything that reads "toy" in ddui comes from rendering, not from immediate mode.

Proposal: both, in two stages. The UI emits a compact DrawCmd list in logical pixels: clip, rounded rect with stroke, glyph run, image, custom callback. That list is hashable, for idle detection and damage rects. A shared tessellator then turns it into one mesh stream in physical pixels, with feathered anti-aliasing and one atlas holding glyphs, icons and the white texel. The vertex layout matches egui's (position, UV, premultiplied RGBA8: 20 bytes). The first backend is SDL2 or SDL3 with GL 3.3, reusing ddui's gl33.d setup. A backend may also consume DrawCmd directly later, for example to use SDF shaders.

/// One draw command. Small and flat, so a frame is one array.
struct DrawCmd
{
    Op op; /// which member is valid
    union
    {
        Rect clip;      /// for Op.clip
        RectCmd rect;   /// for Op.rect
        TextCmd text;   /// for Op.text
        ImageCmd image; /// for Op.image
        uint callback;  /// for Op.custom
    }
}
/// GPU vertex: physical pixel position, atlas UV, premultiplied color. Same layout as egui's.
struct Vertex
{
    float x; /// position
    float y; /// position
    float u; /// atlas coordinate, white texel for untextured shapes
    float v; /// atlas coordinate
    uint rgba; /// premultiplied color
}
/// Fills a convex clockwise path with a `feather` pixel fade to transparent.
void fillConvex(ref Mesh m, const Point[] path, Color c, float feather = 1)
{
    size_t n = path.length;
    uint base = cast(uint) m.vertices.length;
    uint color = c.packed;
    foreach (size_t i; 0 .. n)
    {
        Point prev = path[(i + n - 1) % n];
        Point cur = path[i];
        Point next = path[(i + 1) % n];
        Point n0 = outward(prev, cur);
        Point n1 = outward(cur, next);
        Point avg = Point((n0.x + n1.x) / 2, (n0.y + n1.y) / 2);
        float lenSq = avg.x * avg.x + avg.y * avg.y;
        Point miter = Point(avg.x / lenSq, avg.y / lenSq);
        float h = feather / 2;
        m.vertices ~= Vertex(cur.x - miter.x * h, cur.y - miter.y * h, 0, 0, color);
        m.vertices ~= Vertex(cur.x + miter.x * h, cur.y + miter.y * h, 0, 0, 0);
    }
    foreach (uint i; 1 .. cast(uint) n - 1)
    {
        m.indices ~= [base, base + 2 * i, base + 2 * (i + 1)];
    }
    foreach (uint i; 0 .. cast(uint) n)
    {
        uint j = (i + 1) % cast(uint) n;
        uint ii = base + 2 * i;
        uint jj = base + 2 * j;
        m.indices ~= [ii, ii + 1, jj + 1, ii, jj + 1, jj];
    }
}

Subpixel bins and pixel snapping, the two details that decide whether text and 1 px lines look crisp at 150%:

/// Cache key for a glyph drawn at physical `x`, and the whole-pixel pen position in `penX`.
GlyphKey glyphKey(uint glyph, float sizePx, float x, out int penX, int bins = 4)
{
    float whole = floor(x);
    int b = cast(int) round((x - whole) * bins);
    if (b == bins)
    {
        b = 0;
        whole += 1;
    }
    penX = cast(int) whole;
    return GlyphKey(glyph, cast(uint) round(sizePx * 64), cast(ubyte) b);
}
/// Logical `v` moved to a physical pixel center, for crisp one pixel lines.
float snapLine(float v, float ppp)
{
    return (floor(v * ppp) + 0.5f) / ppp;
}

7.3 Damage and idle

At debugger scale, redrawing the whole window when anything changed costs the GPU almost nothing. The cost to avoid is running frames when nothing changed. Three mechanisms, all cheap:

  • Sleep until input, a requested repaint or a timer (egui's request_repaint_after).
  • Hash the DrawCmd list and skip tessellation and present when it is unchanged (ddui's mu_frame_dirty, generalized).
  • Coalesce backend updates per frame (4.8).

Per-region damage (scissored redraw of changed tiles) is possible later from per-region hashes, but it is not needed to start.

8. Docking

8.1 Data model

Every implementation looks the same underneath: a tree of splits (a direction plus weights) and tab stacks (panes plus the active one), plus floating windows that each hold a tree.

  • egui_tiles 0.18: Tile<Pane> is a Pane or a Container (Tabs, Linear with a direction and Shares, or Grid). A Tree is a root TileId plus Tiles. A user Behavior trait supplies pane_ui, tab titles and simplification options. With serde, the whole tree serializes.
  • egui_dock covers tabs, splits, and dragging tabs out into new egui windows. Its README notes that egui_tiles can divide nodes into more than two children.
  • Dear ImGui's docking branch has dock nodes inside a DockSpace(), layout persisted in the .ini file, and a DockBuilder API that its author calls "not great, it is unfinished, and not well documented".
/// Node of the dock tree.
final class DockNode
{
    Kind kind;            /// split or tabs
    bool vertical;        /// split direction, true stacks children top to bottom
    float[] shares;       /// split weights, one per child
    DockNode[] children;  /// split children
    string[] panes;       /// tab stack contents
    size_t active;        /// selected tab
    DockNode parent;      /// null for a root
    Rect rect;            /// set by `DockSpace.layout`

    /// New tab stack holding `panes`.
    static DockNode stack(string[] panes...)
    {
        DockNode n = new DockNode;
        n.kind = Kind.tabs;
        n.panes = panes.dup;
        return n;
    }

    /// New split of `kids` with equal shares.
    static DockNode split(bool vertical, DockNode[] kids...)
    {
        DockNode n = new DockNode;
        n.kind = Kind.split;
        n.vertical = vertical;
        foreach (DockNode k; kids)
        {
            n.children ~= k;
            n.shares ~= 1;
            k.parent = n;
        }
        return n;
    }

    /// True for a stack with no panes or a split with no children.
    bool empty() const
    {
        return kind == Kind.tabs ? panes.length == 0 : children.length == 0;
    }
}

8.2 Drop targets and drag feedback

While a tab is dragged, find the stack under the pointer, then the zone inside it. The middle region joins the stack as a tab, and the nearest edge splits. Highlight the preview rect. Dropping detaches the pane, inserts it (flattening into a same-direction parent split instead of nesting), and simplifies: empty stacks go, single-child splits collapse, and same-direction nesting merges with shares rescaled.

/// Drop zone for `p` over `target`: the middle half joins, otherwise the nearest edge splits.
static Zone zoneAt(DockNode target, Point p)
{
    Rect r = target.rect;
    if (r.contains(p) == false)
    {
        return Zone.none;
    }
    float fx = (p.x - r.x) / r.w;
    float fy = (p.y - r.y) / r.h;
    if (fx >= 0.25 && fx <= 0.75 && fy >= 0.25 && fy <= 0.75)
    {
        return Zone.center;
    }
    float best = fx;
    Zone z = Zone.left;
    if (1 - fx < best)
    {
        best = 1 - fx;
        z = Zone.right;
    }
    if (fy < best)
    {
        best = fy;
        z = Zone.top;
    }
    if (1 - fy < best)
    {
        z = Zone.bottom;
    }
    return z;
}
/// Moves `pane` into or beside `target`, then simplifies.
void dock(string pane, DockNode target, Zone z)
{
    if (z == Zone.none || (target.panes == [pane]))
    {
        return;
    }
    detach(pane);
    if (z == Zone.center)
    {
        target.panes ~= pane;
        target.active = target.panes.length - 1;
        simplify();
        return;
    }
    bool vertical = z == Zone.top || z == Zone.bottom;
    bool before = z == Zone.left || z == Zone.top;
    DockNode added = DockNode.stack(pane);
    DockNode p = target.parent;
    if (p !is null && p.vertical == vertical)
    {
        size_t i = countUntil(p.children, target);
        float half = p.shares[i] / 2;
        p.shares[i] = half;
        size_t at = before ? i : i + 1;
        p.children = p.children[0 .. at] ~ added ~ p.children[at .. $];
        p.shares = p.shares[0 .. at] ~ half ~ p.shares[at .. $];
        added.parent = p;
    }
    else
    {
        DockNode s = before ? DockNode.split(vertical, added, target)
            : DockNode.split(vertical, target, added);
        replace(target, s, p);
    }
    simplify();
}
/// Simplified replacement for `n`, or null if nothing is left.
private static DockNode tidy(DockNode n)
{
    if (n.kind == Kind.tabs)
    {
        return n.empty ? null : n;
    }
    DockNode[] kids;
    float[] shares;
    foreach (size_t i, DockNode c; n.children)
    {
        DockNode t = tidy(c);
        if (t is null)
        {
            continue;
        }
        if (t.kind == Kind.split && t.vertical == n.vertical)
        {
            float sum = 0;
            foreach (float s; t.shares)
            {
                sum += s;
            }
            foreach (size_t j, DockNode g; t.children)
            {
                kids ~= g;
                shares ~= n.shares[i] * t.shares[j] / sum;
            }
            continue;
        }
        kids ~= t;
        shares ~= n.shares[i];
    }
    if (kids.length == 0)
    {
        return null;
    }
    if (kids.length == 1)
    {
        return kids[0];
    }
    n.children = kids;
    n.shares = shares;
    foreach (DockNode k; kids)
    {
        k.parent = n;
    }
    return n;
}

8.4 Docking in retained and immediate designs

The dock tree is retained data in both designs. Immediate mode walks it every frame, gives each pane a rect and calls the pane's UI function, as egui_tiles' Behavior::pane_ui and Rerun do. Pane state lives in app structs keyed by pane ID, so moving a pane loses nothing. In a retained design the dock tree is the shell, and moving a pane reparents its subtree, which also keeps its state. Docking does not favour either side. Floating windows that become real OS windows (Dear ImGui's multi-viewports, egui viewports) are the hard part in both: one input and render context per window, focus moving between windows, and per-monitor DPI.

9. Hybrid design

9.1 Immediate islands in a retained tree

hybrid.d puts a ddui pass inside a layout node. The tree hands the island a rect, and the island pins a borderless ddui window to it and runs an immediate function there. ddui links unchanged: BetterC code is ordinary D to a normal build. In dentriteui the islands run immediate.d instead (M3), so an island shares layout.d, the renderer, the theme and the widget looks with the tree around it. A 3D view is the simplest island: it gets its rect as a GL viewport and scissor, and draws itself.

  • Invalidation. The island re-runs when a signal it read changes, when it receives input, when its rect changes, or when it asked for animation frames. The pass runs inside an effect, so its reads are tracked. A change only marks the island dirty, and the next frame runs the pass.
  • Input routing. The shell hit-tests the retained tree. The island under the pointer gets events, and an island that saw a press keeps the pointer until release (capture). Keyboard input goes to the focused island.
  • ID scoping. One ddui context per island gives each a private ID space and focus. The alternative is one shared context with mu_push_id(node id) around each island.
  • One command list. Island output is appended to the shell's list behind a clip of the island's rect.
/// Runs the immediate pass if dirty or moved, re-tracking the signals it reads.
void update()
{
    Rect r = bounds;
    if (r != lastRect)
    {
        dirty = true;
    }
    if (dirty == false)
    {
        return;
    }
    dirty = false;
    lastRect = r;
    ++passes;
    if (tracker !is null)
    {
        tracker.dispose();
    }
    bool first = true;
    tracker = effect(() {
        if (first == false)
        {
            dirty = true;
            return;
        }
        first = false;
        pass(r);
    });
}
/// Routes a pointer event to the captured island, else to the island under `p`.
void pointer(Point p, bool down)
{
    Island target = capture;
    if (target is null)
    {
        for (Node n = layout.root.hitTest(p); n !is null; n = n.parent)
        {
            if (Island i = cast(Island) n)
            {
                target = i;
                break;
            }
        }
    }
    if (target !is null)
    {
        target.pointer(p, down);
    }
    capture = down ? target : null;
}

9.2 A debugger skeleton

Under path C the shell is a retained tree built once: menus, the dock area and the panels. The breakpoints panel is panel.d's signal version, and memory and disassembly are islands as in hybrid.d. The backend feeds both through the same mailbox, and a batch of signal writes updates the tree and marks the islands that read those signals.

/// Builds the debugger window once. Signals and islands keep it current.
Node debuggerWindow(App app)

9.3 The reverse: retained-like state inside immediate mode

This is how egui works, and it is the default in A2:

  • small widget state goes in per-ID memory (memoryFor, egui's IdTypeMap)
  • big or persistent state lives in app structs: text buffers, the dock tree, table column widths, tree expansion, scroll anchors
  • whole retained subsystems run inside immediate code: egui_tiles is a retained tree walked by immediate code, and an editor buffer with its undo history is retained data drawn immediately

The rule: if losing it when the widget is not declared for a frame would be a bug, it belongs in app data, not in per-ID memory.

AccessKit is the reference. "The heart of AccessKit is a data schema that defines all the data required to render an accessible UI ... 11. Recommendation and roadmap

11.1 The path

Path C: a retained tree driven by signals (path B), with box-constraint layout and relayout boundaries, immediate islands on dentriteui's own immediate core (path A2), egui-class rendering and text, messages and commands at the app boundary, and the mailbox for the backend.

wait for input, wake or timer (no frame if nothing pending)
 -> drain mailboxes, apply in one batch: effects set node properties, islands that read a signal are marked
 -> route input: hit-test the tree, the node's handlers or the island under the pointer (capture while held)
 -> layout the dirty relayout boundaries (box constraints, cached measurements, list row callbacks)
 -> islands that are marked or moved run their pass in their rect (declare, layout, at most four passes)
 -> paint dirty boundaries into their cached draw lists, island lists clipped to their rect
 -> tessellate (feathered meshes, one atlas) -> render (GL 3.3 first) -> AccessKit update of changed nodes
 -> running animation? request another frame

11.2 Milestones

  1. M0, foundations shared by every path. Text stack (FreeType and HarfBuzz through C bindings, system font fallback later), a glyph atlas with subpixel bins, the DrawCmd to mesh tessellator with feathering, and a GL 3.3 backend on SDL reusing ddui's gl33.d setup. Done when crisp text, rounded rects and 1 px lines render at 100%, 150% and 200%.
  2. M1, layout. Grow layout.d: Stack, Align, Wrap, a scroll view, text leaves with real measurement and a cache, a list with a layout-time row callback, fixed-height rows as their own relayout boundaries, and an assertion on flex inside an unbounded axis.
  3. M2, the retained core. Grow signals.d, layout.d and panel.d into one node tree:
    • node ownership: a component's scope owns its effects and child nodes, and disposing a node disposes them
    • hit testing, pointer capture, hover and focus as node state
    • repaint per boundary: each relayout boundary keeps its draw list, and an unchanged one is reused, as Makepad's cached views are (3.8)
    • a virtualized list over a pool of row nodes, with keyed rows for the panels
    • repaint scheduling (requestFrame, requestFrameAfter, wake from threads)
    • widgets as components (4.9): button, checkbox, single-line text box, slider, menus, popups, tooltips
    B's cost is structural change (11.5), so the pooled list and per-row boundaries come first. Measure build, filter and hit costs with ten breakpoints panels and a one-million-row list, extending bench.d.
  4. M3, immediate islands. Move hybrid.d's islands from ddui to immediate.d, and grow it:
    • a frame arena, with nodes in one array linked by index, as nanoui does (3.2.5), because the GC is most of A2's cost
    • IDs scoped per island, per-ID memory, last-frame hit testing, hot/active/focus
    • declaring again before drawing while a pass handled input, as Ui.frame already does
    • scroll-only events that shift the island's last draw list instead of building it
    • a raw island that hands its rect to GL code, for 3D
    • focus moving across the seam: Tab leaves an island for the next node in the tree, and back
  5. M4, debugger-shaped prototype: the decision point. dock.d with real dragging, tab bars and splitters. The breakpoints panel, a memory view and a disassembly view as islands, a disassembly keyed by address, a log console, and a fake backend thread producing hits at high rate through the mailbox.
  6. M5, the hard parts. AccessKit through accesskit-c and ImportC, IME through SDL3 text input, a multi-line editor, focus scopes and keyboard navigation, theme tokens with hot reload.
  7. M6, platform polish. SVG icons, animation helpers, floating panels as OS windows, clipboard, per-OS quirks.

11.3 What to prototype first

  1. M0's text and tessellator through GL 3.3. It is the largest polish risk and is independent of the architecture choice.
  2. B's breakpoints panel on the real renderer (signals.d, panel.d, layout.d) with a pooled, virtualized list. Measure building, filtering and one hit, and check that per-row boundaries make one hit flat in the list size.
  3. One island on the same renderer: hybrid.d's hex view on immediate.d instead of ddui, next to a GL island that draws a spinning cube. This settles the seam early: input capture, focus moving in and out, IDs, and one theme on both sides.

11.4 Evidence that would justify switching

  • Signals to explicit invalidation (classic retained, as Makepad does), if the signal graph costs more than it saves: effect memory dominates the tree (1.4 KiB per row today), or debugging which effect ran takes longer than finding a missing redraw call. Keep the tree, and replace effects with setters that mark their node dirty.
  • More of the app as islands, if dense views keep turning out simpler to write immediately. C allows it pane by pane, with no switch.
  • C to A2 everywhere, if any of these turns out true:
    • ownership and disposal bugs, reactive debugging time, or D's closure-in-loop capture make the API error-prone in practice
    • structural changes (filtering, rebuilding panels) stay past budget, about 8 ms on a laptop iGPU at full debugger load, even with pooled rows and per-row boundaries
    • keeping focus, IDs and input consistent across the seam keeps producing bugs
    Switching keeps the renderer, the text stack, layout.d, the docking data, the message and command layer, the theme files and widget visuals. An A2 frame then has to stay under about 3 ms at realistic load after the frame arena. The prototype is at about 1 µs per declared row before it (11.5).

The larger sizes are deliberately unvirtualized, so the cost per row shows. Text is fixed-pitch and nothing is rasterized. A1, A2 and D time a whole frame up to its draw list. B times the signal write, its effects and the relayout. A unittest in the same file checks that every path shows the same summary after each operation, and that D draws exactly what A2 draws.   1. At the sizes a virtualized view shows, every path is far under budget. 50 rows cost at most 0.1 ms per update on any path, so ten such panels fit in about 1 ms. Speed does not pick the architecture for this app, which leaves maintainability to pick it (4.2).
  2. A2's extra cost is declaring the tree, which is mostly GC allocation. A2 costs about 1 µs per declared row, three times A1. D with nothing changed skips every declaration, but still lays out, records rects and paints every row. That costs about 0.3 µs per row, the same as A1's whole frame. So layout is not the problem. Allocating about 0.9 KiB of nodes and strings per row is. M3's frame arena targets exactly that.
  3. Collections cause the stutter. With the GC disabled (--DRT-gcopt=disable:1), medians stay the same, but A2's p99 at 1,000 rows falls from 1.8–9.7 ms to 1.2–1.6 ms. A1 allocates only its format strings, and its p99 stays within about three times its median. The frame path should not touch the GC. That means an arena for nodes, reused buffers, and text formatted into scratch space.
  4. D pays off only when little changes. With nothing changed it costs about a third of A2. When everything changed, or on the first frame, it costs 25 to 75% more, because it rebuilds its cache too. That fits its verdict: an optimization for large islands whose content is mostly static.
  5. B is cheapest per change and most expensive per structural change. One hit is 1.3 µs at 50 rows, and a pointer move costs only a hit test. Building the panel or toggling the filter costs about as much as an A2 frame, though, and allocates the most: about 1.4 KiB per row, for the closures and links of each effect. One hit still grows with the list, because the list is one relayout boundary and relayout visits every cached row. Fixed-height rows as their own boundaries would make it flat.
  6. C's island costs what A1 costs for the rows it shows, and nothing while idle.
  7. Kept memory is about the same on A2, D and B: 0.8 to 1.3 KiB per row. That is the tree, the rects and the draw list. D adds its cache, B adds its effects. B's model is five times larger, because every field of a breakpoint is a signal. A1 keeps nothing per row. At 50 rows every path keeps under 70 KiB.
  8. Peak memory follows garbage, not what is kept. A2 throws away 550 KiB per frame at 1,000 rows, and the GC grows its heap to 12–22 MiB for 0.8 MiB of live data. A1 and C never grow it past 5 MiB, at any size.
  9. The default GC keeps old A2 and D frames alive, at random. Across identical runs, A2's kept memory at 1,000 rows read anywhere from 830 KiB to 3.5 MiB, and at 10,000 from 8.3 to 56 MiB. D read up to 1.8 and 18 MiB. A node points to its parent, so one stale word on the stack that looks like a pointer keeps a whole frame's tree. gc:precise scans the heap precisely but the stack conservatively, and one of its runs still kept 46 MiB at 10,000. B, A1 and C build no tree per frame and read the same in every run. An arena fixes this too: a reset frees the frame whatever still points into it, so no node may outlive its frame.

For the retained-first path, findings 5 and 7 matter most. B's cost is in structural change and in the memory of its effects, so M2 starts with pooled rows and per-row boundaries. The frame arena moves to M3, where it serves the islands, for speed and for memory (findings 3 and 9).

11.6 What I was not sure about

  • "egpu". No egui project by that name (the crates.io egpu enumerates external GPUs). Assumed to mean egui on egui-wgpu.
  • The rest of the Craft suite. Only PdfCraft's manifest was checked. The other apps' use of egui is inferred from issue references in the fork's patch list.
  • Every path's cost in D is measured only headless, with fixed-pitch text and the prototypes allocating from the GC (11.5). Real text measurement and a renderer are still the point of M2 and M3.
  • Whether signals are worth their memory in a retained tree, against explicit invalidation as Makepad does it. M4 decides (11.4).
  • Makepad was read on main at 506ec05, 2026-10-31. Its work branch moves daily, and the repository's history starts on 2025-05-06, so the commit counts cover only that span.
  • AccessKit from D is checked only as far as compiling the header with ImportC. Linking the prebuilt library and running an adapter are M5.
  • Snippets in other languages were checked against docs and source, not compiled. The egui checkbox label conversion from String and the SwiftUI @Bindable inside a List row are the least certain.
  • Whether the box-constraint protocol stays enough once real text wrapping meets flex rows: Flutter needs intrinsics for some cases, such as equal-height columns.
  • ddui was read from GitHub at c9bff89, because the local copy is not mounted here. It may differ from dd's working tree.
